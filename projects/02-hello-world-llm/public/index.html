How a message travels
  1. agent.js checks your text first: empty or over 500 characters is stopped here, so it never costs a request.
  2. App Check got an hourly token when the page loaded (reCAPTCHA Enterprise vouched for this page). The browser keeps it and renews it in the background, and every message carries it: no token request per message.
  3. Firebase AI Logic (Google's server) checks the token, adds the Gemini key and sends your message plus the instructions to the model.
  4. Gemini replies; the page shows it as plain text.
How slow replies and errors are handled
  • "thinking…" bubble appears straight away, so you know the message was sent. It's removed when the reply arrives.
  • Send is disabled until the reply comes back: one request at a time, no double-sends from impatient clicks.
  • A fast model: Flash-Lite (name in the green badge) answers quickest and has the most free-tier headroom.
  • Errors become plain messages, never a crash: 403 App Check refused, 429 quota used up, 500/503 model busy, no reply in time, network unreachable. respond() always returns text, so the page can't get stuck on a failure.
  • A time limit: if no reply comes within 90 seconds (the trip to Google and Gemini's reply, plus any wait for an App Check token), main.js stops waiting and you see "No reply came in time…". Free-tier replies can take 20 seconds or more, so the limit is generous; without it, the Firebase SDK would wait 3 minutes, or forever if a token request got stuck.
  • Where the time goes: in the street view, under its step tracker, "Where the time went" shows each stage's real time (the animation is slowed down), and the stage you're waiting on counts up, so you can see which stage a slow reply spent its time in: usually the request to Gemini.

Security features
  • App Check is enforced on Firebase AI Logic: a request without a valid token gets 403.
  • Only our domains get tokens: ragent-eec65.web.app, ragent-eec65.firebaseapp.com, ragents-eight.vercel.app. No localhost, so a copy of this page run elsewhere is refused.
  • Hourly tokens: App Check's token lasts about an hour; the browser keeps it, renews it in the background and sends it with every request. A copied token works until it expires, so the free quota is the backstop (see the next section).
  • Input limit: 500 characters, checked before any request.
  • No script injection: replies are shown with textContent, so a reply containing HTML or a script is just text.
  • Limited browser key: Firebase restricted it to its own APIs; it can't call Gemini directly.
  • No bill possible: the free Spark plan with no billing account. Worst case is "quota used up" (429) until it resets.
Hourly token or a fresh one each time?

App Check can give the browser two kinds of token. This app uses one hourly token: no message makes a token request of its own.

Why we use the hourly token: messages never wait for a token, and reCAPTCHA checks happen about twice an hour instead of once per message. The cost: someone who copies a token could replay it from a script until it expires (about an hour) and use up the free quota. On the free Spark plan that means "quota used up" for a while, never a bill.

In main.js: isTokenAutoRefreshEnabled: true (the hourly token, fetched on page load and renewed) and useLimitedUseAppCheckTokens: false (every request carries it; true would fetch a fresh single-use token for every request).

Why it's safe, and what's still possible
  • Nothing secret is in the page: reading its source, or the public repo, gives nothing that unlocks the model.
  • Copying the page to another site or calling the API from a script fails App Check.
  • Gemini runs on Google's servers, so heavy traffic can't crash anything of ours.
  • Still possible: a patient visitor on the real site can use up the free daily quota, and a token copied from the browser can be replayed from a script until it expires (about an hour). No cost, no data exposed.
  • Still to do: restrict the browser key to our websites, and lower the per-user rate limit (100 → 10 a minute).
  • Type only made-up content: the free tier may use prompts to improve Google's products.

Is my message private on the network? To Review

Short answer: encrypted on the way, so strangers on the network can't read it, but not hidden from everyone.

What protects it

  • HTTPS for the whole trip: the page loads over HTTPS, and the Firebase SDK sends your message to Google's AI Logic endpoint over HTTPS (TLS).
  • .app domains are HTTPS-only: every .app domain is on the browsers' built-in HTTPS-only (HSTS preload) list, so ragents-eight.vercel.app and ragent-eec65.web.app can't be downgraded to plain HTTP.
  • What an eavesdropper sees (same Wi-Fi, internet provider, routers): which Google server you talk to, roughly how big each message is and when. Not the text.
  • Local testing: http://127.0.0.1:5000 is plain HTTP, but that traffic never leaves your computer. The call to Google is still HTTPS.

Who can still see it

WhoWhy
A company network that inspects HTTPS (e.g. Zscaler)It decrypts, inspects and re-encrypts traffic, so the company proxy can read your messages in plain text
GoogleEncryption ends at Google, because the model has to read the message. On the free tier, Google may use prompts to improve its products
Your browserExtensions that can read pages, and anyone at your keyboard (DevTools)

No hosted model avoids the Google row: the provider must read the text to answer it. Only a model running on your own machine (e.g. Ollama) avoids it.

Check it yourself

  1. Press F12 → Network, send a message, and click the request to firebasevertexai.googleapis.com: it's https://, and only your browser shows the body in readable form.
  2. Click the padlock in the address bar → the connection's certificate → Issued by. Behind an inspecting proxy it names the proxy (e.g. Zscaler), not Google: that's the proof it's being decrypted.

How to keep it more private

  1. Don't send anything sensitive: only made-up content here. This matters most.
  2. Use a personal device on a personal network, which takes the company proxy out of the path.
  3. A paid Gemini plan if Google must not use prompts for training.
  4. A Content Security Policy on the site, so an injected script can't send messages elsewhere (not added yet; it can't stop browser extensions).
  5. A local model (e.g. Ollama) if nothing should leave the machine.
