What you learn
  • Runnables: LangChain's building block. agent.js turns plain functions into Runnables with RunnableLambda.from(fn) and names each one, so it shows up by name in LangChain's reports.
  • .pipe(): joins Runnables into a chain. normalize.pipe(rules) feeds normalize's output into rules, and chain.invoke(text) runs the whole chain and returns { reply, rule }.
  • RunnableBranch: if/else as a chain step. It tries each condition in order (is empty? → is greeting?) and runs the reply step of the first one that's true, or the default.
  • streamEvents(): LangChain reports each step as it runs (on_chain_start, on_chain_end, with names and outputs). The street view and the diagram below are drawn from that report.
How a message travels
  1. index.html: the form's "submit" event runs onSend(e), which adds your bubble and calls chain.invoke(text).
  2. normalize (a RunnableLambda in agent.js) trims the text. .pipe() hands the result to rules.
  3. rules (a RunnableBranch) asks: is it empty? Is it a greeting (hello, hi or hey as the first word)? If neither, it takes the default. The reply step it picks returns { reply, rule }.
  4. onSend(e) gets that object back and shows result.reply with add().
  5. For the street view and the diagram only: once the reply is on screen, the page runs the chain a second time with streamEvents() and records what LangChain reports. Both replay that recording slowly.

The real trip takes milliseconds. "Where the time went", under the street view's tracker, shows each stage.

What leaves your browser
  • Your messages: nothing. There's no model and no server call: the chain runs in this tab. The street view counts the page's network requests from your first message on, and it stays at 0.
  • LangChain's code comes in, once. When the page loads, the import map points @langchain/core/runnables at jsDelivr, a public CDN. That one import brings in about a dozen files: LangChain's runnables plus the packages they use (langsmith, zod and a few small helpers). The street view lists the real requests. Send stays off until they've all arrived.
  • The page's own files (index.html, agent.js, style.css, the extras) come from this site's server, also once.
  • LangSmith tracing is off. LangSmith is LangChain's hosted tracing service. Its client code is among the downloaded files, but LangChain only sends traces when tracing is switched on (a setting such as LANGSMITH_TRACING=true, which a web page doesn't have), and nothing on this page switches it on. The to-do card below lists what real tracing would need.
  • What jsDelivr sees: each file request, with your IP address and this site's address, like any download. Never what you type.
Why LangChain, for three rules?
  • Same replies as step 1 (the tests compare them, message by message), so only the shape changes.
  • One interface for every piece: a function, a prompt, a model and a tool are all Runnables. A later step can swap reply: fallback for a model and keep the rest of the chain.
  • A report for free: streamEvents() describes each step with no extra code in agent.js. It's built on the same tracer callbacks that send LangSmith traces when tracing is on.
  • The cost: about 0.3 MB to download (about 1.2 MB of JavaScript once unpacked) to do what step 1 does in a few lines, plus a CDN the page depends on. It pays off as the chain grows; for Hello World alone it's overkill.
Limits
  • It still only knows greetings: step 1's rules, no model, no memory between messages.
  • It needs jsDelivr when the page loads. If the CDN is blocked or offline, the chat says it couldn't load LangChain and Send stays off. Once the page has loaded, it works offline.
  • The first visit waits for LangChain's files before Send turns on; later visits usually get them from the browser's cache.
  • The street view and the diagram show the second, recorded run. It gives the same reply (same rules, same text), but it's usually slower than the real call, because LangChain reports every step.
  • Times are only as exact as the browser's clock, which moves in small steps on purpose (0.1 ms in Chrome and Edge), so times under a millisecond are approximate.
Safety, and what's still possible
  • No keys, no secrets, no backend: nothing on this page unlocks anything, and there's no quota or bill to run up. The chain runs on your own computer.
  • No script injection: your text and the replies go on the page with textContent, so HTML in a message is shown as plain text.
  • A pinned version: the import map asks for @langchain/core@1.2.17, the version package.json pins for the tests, so a new @langchain/core release can't slip in. Only that one package is pinned here: the next point covers the ones it imports.
  • Still possible: nothing checks the downloaded code. The import map has no integrity hashes, and jsDelivr generates these +esm files itself (each one starts with its own note: "Do NOT use SRI with dynamically generated files!"). The versions of the packages @langchain/core imports (LangChain's own langsmith, zod and a few helpers) are written into jsDelivr's file, not chosen by this repo: today they match the tests' node_modules, but if jsDelivr ever rebuilt the file, newer ones could come in. So the page trusts jsDelivr and npm: altered code would run here with full access to the page, including what you type.
  • Also possible: a company proxy that inspects HTTPS (e.g. Zscaler) sees, and could change, the files this page downloads. It never sees your messages: none are sent.
  • To close the gap (not done yet): serve LangChain from this site, bundled at build time from the tested node_modules, with integrity hashes, plus a Content Security Policy that only allows this site's scripts.
